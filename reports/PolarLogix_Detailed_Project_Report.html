POLARLOGIX / OPERATIONS
PRODUCT, TECHNICAL & OPERATIONAL REVIEW

Detailed Project Report

How the application works, its workflows and technology, the real-world problem it addresses, and its feasibility and business potential.
Assessment at a glance
PolarLogix is a credible operations-console prototype for coordinating polar expeditions, cargo, station sustainment, personnel and incidents. It is suitable for demonstrations and controlled shadow-mode evaluation, but should not yet be treated as an authoritative safety-critical command system. Several prominent live-looking displays are seeded, static or simulated.
Prepared: 25 September 2026
Product: PolarLogix Operations
Review basis: Source code, routes, API and schema
Audience: Product, engineering, operations and decision-makers

Executive summary

PolarLogix Operations presents a single command-centre interface for a complex expedition supply chain: stations, voyages, cargo, inventory, people, field parties, equipment and emergency response.

The strongest product idea is not a map by itself. It is exception coordination: show how an operational event affects related areas, record decisions, and help the team recover with a shared picture. The application has an authenticated web console, an API-backed snapshot and mutations, a Supabase persistence layer, and source-defined data models for the main domains. There is enough functionality for a compelling end-to-end prototype and a carefully bounded pilot.

Operational-use boundary. “Live” wording does not consistently mean live telemetry. The map animates seeded positions; India cargo lanes are labeled demonstration lanes; several sensor, weather and readiness metrics are fixed display values; offline queue count is always zero; and browser polling is not a realtime transport. The application explicitly says “NO LIVE NAVIGATION CONTROL.” Use simulated information only for rehearsal until real data feeds, permissions, resilience and safety assurance have been validated.

2. The real-world problem and proposed solution

Problem

Polar logistics combine long-distance transport with isolated stations, limited resupply windows, scarce fuel and life-support inventory, cold-sensitive cargo, weather restrictions, personnel accountability, specialized equipment and emergency response. In fragmented workflows, different teams may hold separate spreadsheets, sensor portals, radio logs and mission plans. A condition change can require multiple teams to reconcile those records quickly while connectivity is limited.

Proposed solution

PolarLogix presents one cross-module operations picture. It aims to put expedition milestones, station occupancy and weather, cargo condition, inventory consumption, personnel state, assets, field parties and incident decisions in one console. Its emergency cascade concept shows a common incident alongside selected consequences in cargo, voyages, fuel forecast and field movement, with an event trail.

3. Application pages and features

The authenticated shell exposes eleven primary modules. A twelfth route, /runbook, provides a guided rehearsal but is not one of the main sidebar modules. Unknown paths show a “Signal not found” screen. Mobile navigation opens the same main modules in abbreviated form. The signed-in shell includes operator identity, sign-out, UTC clock, station summary and a refresh/network indicator.

3.1 Public landing and access

Routes: / when signed out, /sign-in, /sign-up. The branded landing page describes a “Secure Command Console,” displays static at-a-glance counts (04 station nodes, 03 voyages, 09 tracked units, 24/7 coverage), and explains central approvals, multimodal tracking and readiness at a glance. Users can choose Sign in to Command or Create Operator Account. Clerk provides the authentication screens. These landing-page counts are presentation content, not a live operational snapshot.

3.2 Operations overview — Command centre at a glance (/)

  • SIMULATE CONDITION 1: invokes the blizzard/emergency cascade. When active, it becomes a Condition 1 Active state; the page displays a cascade-propagated alert and links to Emergency Command.
  • Active Voyages: counts voyages in UNDERWAY or DELAYED states; includes a delayed-voyage detail.
  • Personnel Accounted: counts non-SOS people out of the roster total; shows field count.
  • Cargo Exceptions: counts CRITICAL cargo and surfaces cold-chain and shock-watch information. Shock watch uses a threshold of 1.5 g.
  • Fuel Coverage: estimates fuel days as quantity divided by daily burn; the display applies an 18% emergency uplift.
  • Theatre status: station cards show code, coordinates, theatre, weather, occupancy/capacity and operational status. A Personnel link opens muster details.
  • Activity feed: shows a small recent-event subset with UTC time, module, action and color tone.
  • Operator approvals: shows seeded requests with operator, role, priority, request ID, request text, station and submit time. Approve/Reject records a local browser decision and emits an AUTHORITY event. The decision itself is not a durable server-side authorization record, so it is not a reliable access-control workflow.

3.3 Expedition control — Voyage planning (/expedition)

  • Headline cards show next ice entry, fleet readiness and path risk. These include fixed demonstration values.
  • The ice-corridor timeline shows port departure, Southern Ocean, ice entry, station offload and return window; badges are complete, active and next.
  • Voyage rows show expedition ID, vessel, polar-class label, route, departure, ice-entry estimate, status and delay. OPEN shows a voyage record, navigation-state text, destination/logistics cell and weather-watch summary.
  • MARK READY / RELEASE UNDERWAY / HOLD or DELAY changes voyage status through the API and refreshes the view.
  • CREATE VOYAGE opens a mission builder with vessel, destination and departure-window fields. Saving creates a plan record with a generated expedition identifier and derived route/class values. Some fields (such as entry timing) are currently fixed/defaulted rather than calculated by a route-optimization engine.

3.4 Cargo telemetry — Cold-chain and stowage (/cargo)

  • SIMULATE ANOMALY writes a critical temperature anomaly for sample tracking ID PLX-804-19, then refreshes the snapshot.
  • Summary cards show container counts, cold-chain pass percentage, total mass and LIVE SENSORS/heartbeat. These are fixed display/demo metrics, not proof of an attached sensor fleet.
  • The temperature trace displays a sample sensor series and a tolerance band of −20°C to −12°C. Its plotted points are static.
  • The container grid presents Bay 03, Maitri inbound and a locked crane sequence as sample stowage context.
  • Search filters telemetry rows by tracking ID, description or destination. Row fields include tracking, description, cargo type/weight, destination, temperature °C, shock g and state. The visible legend uses NORMAL (cyan), HOLD (amber) and EXCEPTION (red); the underlying API commonly represents the critical state as CRITICAL.

3.5 Inventory and burn — Sustainment picture (/inventory)

  • Cards display critical-stock count, fuel runway in days and combined water/oxygen life-support coverage. Emergency mode shows an 18% burn uplift and a lower runway.
  • The fuel runway chart projects litres remaining at D0/D4/D8/D12/D16/D20. Generator, aviation and water-treatment draw rates are shown in L/day. These projection curves/draw assumptions are presentation/demo profiles, not forecasts derived from a full demand model.
  • The VED register shows item name/SKU/category/station, on-hand quantity and unit, daily burn, threshold and a visual bar. A row’s − / + controls apply a −10 / +10 adjustment via the API and create an inventory event.

3.6 Personnel readiness — Muster and field safety (/personnel)

  • Cards count accounted people, active field personnel and a readiness index.
  • Roster entries display person, role, station/phase, medical, training, blood group and operating state.
  • INDOOR, FIELD, SOS update a person’s status through the API and add an event. The UI explains Indoor/Station as sheltered and accounted; Field/Beacon as active work parties; SOS/Response as immediate response required.
  • RECONCILE MUSTER currently shows a confirmation alert; it does not reconcile an external roster or beacon feed.

3.7 Emergency command — Command the cascade (/emergency)

  • TRIGGER CONDITION 1 invokes a seeded Maitri blizzard incident with severity LEVEL_3_LIFE_THREATENING, type BLIZZARD_COND_1 and lockdown enabled. The visible alert describes field movement suspension.
  • The application updates incident state and selected cargo/voyage records, displays personnel movement as recalled, cargo handling paused, generator forecast elevated by 18%, and milestones pushed. The screen is a cross-module response summary, not a complete automation of all field SOPs.
  • DECLARE RECOVERY resolves the active incident. Recovery does not guarantee that every secondary data change is rolled back.
  • A weather card shows a sample whiteout, visibility under 120 m and wind at 42 kt. The event log lists recorded cascade events. The phrase “badge readers require command release” is interface copy; no badge-reader integration is evidenced.
  • A lockdown control performs the same trigger/recovery path. Active state changes the global warning banner and disables/restricts selected actions.

3.8 Asset management — Fleet and equipment (/assets)

  • Groups assets by VEHICLE, GENERATOR, SCIENCE INSTRUMENT and CONTAINER. Cards summarize registered assets, items in use and maintenance due.
  • Rows show ID, name, V/E/D mission criticality, location, status and next-service text. OPEN RECORD shows a detail modal, readiness check and movement restriction.
  • Asset controls mark an item IN USE, return it to READY or clear a service flag. Vehicle movement is disabled during emergency state.
  • The “3D asset profile” is a decorative CSS visual, not a 3D model, digital twin or live equipment connection.

3.9 Map and corridors — Multimodal operating picture (/map)

  • An interactive Leaflet map shows station nodes, vessels, tugs, helicopters, UAVs, routes and cargo lanes. Marker popups can open unit/cargo/voyage records.
  • Legend: teal dot station; yellow dot vessel; teal dot tug boat; purple dot helicopter; slate dot UAV; cyan dashed India lane; yellow dashed open route; red dashed restricted route.
  • Unit records show current position, speed in knots, route/ETA, mission link and cargo manifest particulars. India-lane popups show origin/destination, mode, loads, speed, “MOVING,” and explicitly “LIVE SIMULATION.”
  • Demonstration lanes are Chennai→Maitri (SEA / PC-6), Mumbai→Bharati (SEA / PC-5), and Kochi→Himadri (AIR / SEA RELAY). Movement is generated locally from fixed route points, progress and speed parameters; it is not GPS/AIS/ADS-B or vessel-provider telemetry. Animation updates on a 900 ms UI timer.
  • OpenStreetMap tiles provide the visual map. “Corridors open/restricted” summarizes application state; it is not navigational authorization. The page explicitly presents the India lanes as demonstration lanes.

3.10 Field companion — Work-party console (/field)

  • Shows a beacon/sortie status badge, field-active count, a next check-in card and visibility summary. Values such as next check-in 06:15 and visibility 8.4 km / under 120 m are sample display values.
  • Lists person, role, station, blood group and state. Controls set a person Sheltered/Indoor, Field or SOS. Field can be disabled during emergency.
  • During an active incident it displays Field Movement Suspended and instructs return to shelter and beacon confirmation. The schema contains field-sortie concepts, but the current screen changes person status; it is not an end-to-end beacon or sortie dispatch system.

3.11 Audit and reports — Decision record (/audit)

  • Lists UTC, module, command and justification. When justification is missing, the UI shows a default phrase.
  • EXPORT CSV creates a client-generated CSV from currently loaded events. PRINT / PDF calls the browser print dialog; it is not a server-generated, immutable report.
  • “AUDIT APPEND-ONLY” is a UI label. Event rows are persisted by API, but database immutability controls and complete actor/authorization attribution need verification before treating the records as legally tamper-proof.

3.12 Scenario planner — Test the cascade (/scenarios)

  • Three cards: Weather degradation (Maitri whiteout), Vessel delay (shift a voyage by one day), and Cargo telemetry failure (inject a cold-chain exception).
  • Controls run the selected scenario and, when active, declare recovery. The page labels itself LOCAL SIMULATION, STATE IS REVERSIBLE and NO LIVE NAVIGATION CONTROL.
  • Important behavior distinction: scenario actions call API mutations and can alter persisted records; “local simulation” describes the scenario framing, not a guaranteed throwaway sandbox. Use only with designated demo/test data.

3.13 Demo Runbook — Operations rehearsal (/runbook)

Four clickable steps guide a rehearsal: Establish picture (overview/station status/log), Detect anomaly (cargo failure or vessel delay), Execute cascade (weather/emergency), and Recover & report (resolve and export audit). “OPEN MODULE” navigates to the corresponding operational area. This is a walkthrough, not an independent workflow engine.

4. End-to-end project workflows

4.1 Normal operations review

  1. Operator signs in through Clerk.
  2. The client requests the authenticated operations snapshot.
  3. The API reads operational rows from Supabase and maps them into the client’s common snapshot shape.
  4. Operator reviews station, voyage, cargo, inventory, personnel and asset status across modules.
  5. The browser polls again every 10 seconds; successful snapshot loading is presented as SYNCED/LIVE OPERATIONS FEED.

4.2 Voyage planning and status control

  1. Review the voyage list and timeline.
  2. Open an existing voyage to inspect route/status/ETA details.
  3. Mark ready, release underway, or hold/delay; each action updates the voyage through the API.
  4. Optionally create a plan by choosing a vessel, destination and departure window.
  5. Snapshot refresh makes the updated state visible. Route timing and some plan fields remain seeded/defaulted rather than computed from external conditions.

4.3 Cargo exception handling

  1. Search for a cargo tracking number or destination.
  2. Review temperature, shock, destination and status.
  3. Use the simulation control in demo mode to append a sample anomaly, or receive an API-backed anomaly record.
  4. Review the new state and related event after the refreshed snapshot.
  5. Real-world use would additionally need a sensor source, raw readings, calibration, chain-of-custody, triage and approved disposition.

4.4 Emergency cascade and recovery

  1. Declare Condition 1 / trigger the seeded blizzard incident.
  2. The API records the incident and updates selected related data (including targeted voyage/cargo changes).
  3. The overview banner and Emergency screen communicate restricted movement, paused handling, forecast uplift and milestone impact.
  4. Operators use the event log to review changes, then explicitly declare recovery.
  5. Recovery resolves incident state; it is not an atomic rollback of all secondary changes. Multi-write failures could leave partial effects.

4.5 Inventory adjustment and runway

  1. Review on-hand, daily burn and threshold.
  2. Adjust stock in fixed increments of ten units.
  3. The API writes the quantity update and a corresponding operation event.
  4. The client refreshes; the runway display estimates coverage from quantity and burn profiles. This is not a complete procurement or demand-planning process.

4.6 Muster, field state and audit

  1. Review roster and station assignment.
  2. Set each person to INDOOR, FIELD or SOS as applicable.
  3. Emergency state can restrict field action and raise a global banner.
  4. Changes create operation events visible to authorized users through the snapshot.
  5. Export currently loaded events to CSV or open print/PDF from the browser.

5.2 Request and persistence path

Browser → API → Supabase → API response → browser. Clerk renders the access flow. After authentication the client fetches /api/operations. The Express API checks for a Clerk user, uses a server-only Supabase service-role client to load/map the snapshot, and returns domain data. User actions call operations endpoints; server code writes to Supabase; the frontend refreshes after the mutation.

The API supports GET /api/healthz; GET /api/operations; POST /api/operations/voyages; PATCH /api/operations/voyages/:id/status; POST /api/operations/inventory/adjust; PATCH /api/operations/personnel/:id/status; PATCH /api/operations/assets/:id/status; POST /api/operations/cargo/anomaly; POST /api/operations/emergency/cascade; POST /api/operations/emergency/resolve; POST /api/operations/events; and POST /api/operations/initialize. Health check only confirms the server responds; it does not validate database reachability or authentication.

6. Feasibility, viability and business model

6.1 Technical feasibility

Feasible as a controlled pilot: the code already separates browser, API and database responsibilities, and the schema has domain entities for cargo, inventory, incidents, people, assets and spatial data. A real pilot can build on these components instead of starting over.

Not ready as safety-critical infrastructure: authoritative movement/sensor feeds, true offline operation, robust data freshness, permissions, recoverable transaction behavior, field-tested interfaces and safety assurance are not demonstrated. A service-role database client behind a generic authenticated API makes server-side authorization especially important; authenticated access alone is not the same as role-based permission to issue an operational command.

6.2 Commercial viability

A specialized polar operations platform could be valuable to national research programmes and expedition operators if it measurably reduces coordination time, cargo loss, stockout risk or incident-response delay. The buyer may be an operations director or central IT/procurement organization, while daily users span stations, logistics, cargo and safety teams. This is a plausible market hypothesis only. The reviewed project contains no signed customer, user study, procurement route, willingness-to-pay evidence, cost model, support SLA or proof of measurable benefit.

6.3 Business model options (hypotheses, not current offers)

  1. Paid institutional pilot + implementation: a 6–12 month scoped deployment with configuration, integration, training and support, followed by an annual platform/support contract.
  2. Annual programme license: price per research programme, station group or theatre, with modules for cargo, sustainment, personnel/emergency and audit. Use support/integration tiers; avoid assuming cargo tonnage correlates with safety value.
  3. Managed operations service: hosted platform with data-quality monitoring and support coverage. This adds sovereignty, data-residency, staffing and liability obligations.
  4. Hardware/software bundle: rugged edge gateway plus sensor/beacon kits and connectivity. Potential differentiation, but materially higher certification, field service, battery and support costs.
  5. Adjacent-market expansion: Arctic research and other remote expeditions are possible later segments, but require separate workflow and buyer validation.

6.4 Evidence required to establish viability

  • Interviews with central command, station commander, reefer/cargo lead, field-safety officer, maintenance and IT/security stakeholders.
  • Confirm the current toolchain and prove which handoffs are actually slow or error-prone.
  • Measure a baseline: unlocated cargo, cold-chain excursion dwell time, stockout alerts, muster completion time, delay attribution and data freshness.
  • Quantify integration and field-support cost, procurement lead time, security review, data residency, ownership and acceptable deployment model.
  • Test a buyer-funded pilot and willingness to renew before forecasting revenue or market size.

Phased path

  1. Label and isolate: separate demonstration records from operational records; visibly identify every simulated/static value.

9. Conclusion

PolarLogix has a clear operational concept and a well-structured prototype footprint. Its strongest demonstration is the way it brings station status, voyage planning, cargo condition, stock runway, people, equipment and incident history into a single interface. Several core state mutations are backed by the API and Supabase, so this is more than a static visual mockup.

At the same time, this review did not find evidence that the product currently receives authoritative live vessel positions, live cargo sensors, verified weather, actual beacon/radio data, or a durable offline queue. Some demonstration controls can write to the database; simulated and sample data therefore need explicit isolation. Authentication is present, but per-role command authorization and formal operational sign-off are not demonstrated.

Decision recommendation: continue product development toward a bounded, paid or sponsored institutional shadow-mode pilot. Start with the cargo exception and sustainment workflow; measure user and operational outcomes; use the system in parallel with existing authoritative processes. Do not enable autonomous navigation or safety-critical command reliance until data provenance, offline behavior, role controls, failure recovery, field usability and safety assurance have all passed agreed acceptance tests.

Commercially, an institutional pilot followed by an annual programme license or managed platform is a credible hypothesis. Whether it is viable depends on proving a buyer, procurement path, measurable operational value and support economics—not on the feature set alone.
